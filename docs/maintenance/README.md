# 文件夹与代码整理方案

日期：2026 年 10 月 28 日。**本文件是下一轮整理计划，尚未执行批量删除或移动。**先完成4.6.4并保留验收结果，再按下面的顺序整理。

## 一、现在主要是什么占地方

以下是本机文件大小，使用十进制GB/MB；不代表GitHub仓库大小。未计入`.git`和Docker外部数据卷，缓存与日志会继续增长。原始结果见 [目录盘点](folder-inventory.json)。

| --- | --- | --- |
| `.local/` | 约19.03 GB | 主要是工具、编译产物、缓存和迁移记录，不能整目录删除 |
| `.local/rust-target/` | 约11.66 GB | 当前与旧版编译产物混在一起，可重建；清理后需要重新构建 |
| `.local/migration-20261023/` | 约4.12 GB | 包含迁移前的编译产物、原文件及检查记录，先区分备份和缓存 |

## 二、哪些保留，哪些可以整理

| 内容 | 处理办法 | 做之前先检查什么 |
| --- | --- | --- |
| `apps/web/`、`services/api/` | 保留正式前后端 | 只拆分过长文件，不删除已使用功能 |
| `migrations/` | 五个版本全部保留 | 已执行的SQL不能重写或合并成一个新文件 |
| `deploy/`、`.local/uploads/`、Docker数据库数据卷 | 保留真实配置、上传文件与数据 | 它们不是编译缓存；备份时同时考虑数据库与文件 |
| `.local/cargo/bin/`、`.local/rustup/` | 保留当前使用的工具 | 若删重复工具版本，先确认`rust-toolchain.toml`及脚本所需版本仍在 |
| `.local/dev-processes.json` | 交给停止脚本处理 | 不能在程序仍运行时随手删掉，避免失去停止入口 |
| `.local/rust-target/` | 停止程序后清理旧编译产物，再重建一次 | 清理会移除本机API程序，不会删除源码；重建成功后才能重新启动 |
| `.local/migration-20261023/rust-target-before-rebuild/` | 优先清理的旧编译备份 | 确认迁移完成、当前项目能构建；保留同级`originals`和迁移记录直到外置归档完成 |
| `checks/web-smoke/node_modules/`、`checks/web-smoke/.next/` | 可清理的早期示例产物 | 保留示例源文件、锁文件和检查结果；若要再跑旧示例，重新安装构建 |
| `.local/fras-frontend/` | 可清理的参考前端构建副本 | 原始快照在`.upstream/`，检查结论在`checks/results/`；先确认副本没有独有修改 |
| `apps/web/node_modules/`、`apps/web/.next/` | 非必要不动，缺空间时再清理 | 正式前端仍在使用；停止网页后处理，随后执行`npm ci`和构建 |
| `.local/*-tests/`、`.local/logs/` | 只清理已结束的测试和过期日志，保留最近一轮证据 | 测试文件目录与真实`.local/uploads/`不同；数据库清理由验收脚本处理 |
| `.requirements_work/` | 外置归档旧稿与大图，项目内只保留说明及必要结果 | 先保留原Word、最终稿、恢复所需脚本和许可；文档工作目录可能含旧配置，不自动上传GitHub |
| `Old_docs/`、`.upstream/` | 后续统一放到归档区 | 移动时同时修改文档链接及旧检查脚本路径，保留原仓库许可与版本记录 |
| `docs/page-drafts/` | 保留设计参照，后续可归档为独立预览包 | 它不是正式前端；字体路径与双击预览仍要能用 |
| `demand/提交文档模版.zip`及解压目录 | 先保留，核对一致性后再决定保留哪份 | 先确认实际用于课程提交的是哪份，不能直接按“同名”删掉 |

本次没有删除上述内容。原Word、参考源码、课程模板和现有账号保持原样。

## 三、推荐保留的目录结构

先保持正式代码的位置不变，避免启动和部署脚本全部重写。后续整理后的目标如下，`archive/`和`scripts/test_support/`目前尚未建立：

```text
项目根目录/
├─ README.md                     总入口、4.6成果和日常命令
├─ 邮智汇_程设项目计划书.md        后续阶段任务
├─ 邮智汇_当前成果汇报.md          实际完成情况
├─ apps/web/                     正式前端
├─ services/api/                 正式后端
├─ migrations/                   不改写的数据库版本
├─ deploy/                       运行配置与容器定义
├─ scripts/                      正式准备、启动、停止和验收命令
│  └─ test_support/              后续共用的测试辅助代码
├─ demand/                       当前需求、原Word及参考分析
├─ docs/
│  ├─ design/                    页面、字段、接口与权限约定
│  ├─ engineering/               日常运行说明
│  ├─ accounts/ forum/ goods/ chat/  各功能说明与验收记录
│  ├─ acceptance/                4.6整体验收、范围与修复记录
│  └─ maintenance/               本整理计划和盘点
├─ archive/                      后续归档，不是正式代码
│  ├─ preparation-checks/        早期示例与检查结果
│  ├─ reference-code/            三个参考仓库及版本说明
│  └─ early-docs/                早期讨论与页面草图
└─ .local/                       工具、真实上传、缓存、日志分开放
```

`demand/`继续保存当前需求；正式代码仍按前端和后端分开。不要把需求、历史备份和运行代码再复制成多套“最终版”。

## 四、代码可以怎样减掉重复

### 4.1 先解除工具脚本对checks的依赖

`scripts/Use-DevEnvironment.ps1`仍调用`checks/Use-ProjectTools.ps1`。将工具路径设置移到`scripts/`，让正式命令使用新位置，旧检查脚本暂时保留转调入口；验证成功后再归档旧示例。`Cargo.toml`还排除了`checks/rust-smoke`，移动示例时要同步检查此处。

### 4.2 合并测试辅助代码，保留不同测试场景

目前测试脚本按`verify_runtime → verify_accounts → verify_forum → verify_goods → verify_chat → verify_acceptance`逐层复用，且通过模块变量设置日志目录。后续把临时数据库、启动停止、HTTP客户端、上传样例和WebSocket客户端集中放到`scripts/test_support/`，测试文件只描述各自场景，日志路径由参数传入。

保留账户、论坛、商品、聊天和跨模块检查，不能因为都出现“登录”“数据库故障”就删除其中一份：它们验证的业务写入不同。所有测试仍顺序运行，直到将端口和容器也真正隔离。

`apps/web/checks/money.test.mjs`是仍在执行的金额测试，不是废弃代码。可改放`apps/web/tests/unit/`，同时更新引用路径、PowerShell命令和CI。

### 4.3 拆分前端大文件，不改页面地址

`forum.js`、`goods.js`、`chat.js`把多种页面放在同一文件，后续按“列表、详情、编辑、管理”拆开。先统一列表读取、错误提示和权限变化时清除旧内容的方法，再逐个替换，避免同名方法行为不一致。

论坛和聊天各有一套列表读取方法：聊天会保留后台刷新前的内容，论坛会清空。合并时必须保留这一差异需要，并防止切换账号后短暂显示上一账号的数据，不能直接删掉其中一份。

### 4.4 说明和字体只保留明确的一份来源

日常启动步骤以`docs/engineering/README.md`为准，其他说明只链接到它；状态以根README、成果汇报和整体验收表为准，历史结果保留原日期。

正式前端与HTML草图各有一份相同中文字体。若要合并，先改字体路径，再分别验证正式网站和双击HTML；归档整个草图包时可保留包内字体及许可，不必为省少量空间破坏预览。

数据库中AI、监控、举报相关表虽尚未接入业务，但已用于后续设计和迁移，不作为“暂时没调用的死代码”删除。`/dev-check`仍用于工程验收；生产环境按配置关闭开发接口，退役它时要先修改对应检查。

## 五、按什么顺序做

| 顺序 | 任务 | 完成时应看到什么 |
| --- | --- | --- |
| 1 | 保留本轮验收记录，盘点并备份真实配置、数据库、上传文件 | 知道哪些是数据、工具、缓存和历史资料 |
| 2 | 清理旧编译备份、示例依赖、过期测试文件和日志 | 空间下降，正式代码和真实上传不变 |
| 3 | 迁移共用工具设置，再归档checks和旧资料 | 正式启动命令不再依赖归档目录，所有文档链接可用 |
| 4 | 合并测试辅助代码，再逐个拆分前端文件 | 少重复、容易读，页面地址与既有功能不变 |
| 5 | 重新准备、构建和执行完整4.6验收 | 同一条流程通过，原账号、已保存数据和旧文件权限正确 |

每次只做一类移动或删除，记录改了哪些路径，再进入下一项。新成员应能只看根README就找到启动、功能、验收和需求入口。
