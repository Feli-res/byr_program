## 二、本轮具体检查了什么

### 2.1 同一批数据的完整流程

两个独立浏览器分别登录卖家、买家。卖家带图发帖，买家回复、点赞收藏并刷新；卖家发布带图商品，买家通过搜索和价格/校区筛选找到商品，返回列表时条件仍在，再联系卖家、发送消息，确认对方收到真实WebSocket事件，最后查看通知、标为已读并刷新。

完成网页操作后，另外通过HTTP读取保存结果；再重启网页、API及数据库，核对同一篇帖子、回复、精确价格、会话历史及通知已读仍在，不能只凭页面出现气泡判定保存成功。

### 2.2 页面状态与恢复

检查加载、无结果、非法价格、未登录、无权限、读取失败和保存失败。受控拦截只用于稳定重现网页加载/503状态；真实MySQL、Redis停止与恢复由原工程、账户、论坛、商品和聊天验收继续检查，两类结果分别记录。

另按普通用户17个、管理员5个入口逐页访问，共22个页面入口，检查375像素窄屏及相应身份下的页面显示；缺失帖子/商品显示错误状态。

失败时保留当前输入，不跳到成功页；恢复后可重新提交。浏览器重新加载前先等待后端保存结果，避免把取消中的请求误判为保存失败。

### 2.3 管理操作同时影响各处

对同一篇帖子执行隐藏、同一件商品执行管理下架，检查：搜索结果排除、旧附件地址拒绝、聊天中来源商品改为不可用、通知不泄漏旧标题。管理员及无关用户均不能读取双方私聊。

### 2.4 登录失效影响全部业务

改密后复用旧登录，分别尝试修改帖子、修改商品和发送私聊，全部拒绝；旧实时连接小于5秒关闭。新密码重新登录可以操作，管理员封禁后再次拒绝写入，另一方也不能向被封禁用户发送新消息。

原有验收继续覆盖版面授权、重复点赞收藏、并发编辑、消息幂等、文件归属与超限、五种登录失效、数据库故障和重启。未在跨模块测试中重写所有旧场景。

## 三、怎样重新检查

先打开Docker Desktop，再停止本机开发程序，执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/Verify-Acceptance.ps1
```

此命令只构建一次，再顺序运行工程、账户、论坛、商品、聊天回归及新的跨模块验收。检查会真实停止重启开发专用MySQL/Redis，不要和日常开发或其他验收同时运行。结束后使用原启动命令重新打开网站。

已完成构建、只需重跑跨模块场景时，可运行`python scripts/verify_acceptance.py`；加`--regressions`才会同时重跑所有旧验收。Linux/WSL按工程说明准备，安装账户与聊天测试依赖后使用`python3`执行同一脚本。

新的跨模块场景有3个真实浏览器测试和8组检查。测试库名为随机的专用名称；结束后撤销该库授权并删除临时库。开始、结束时在内存中比较原来三个账号的完整用户行，结果一致；账号内容和密码哈希不写入报告。日志、合成图片与截图在被忽略的`.local/logs/acceptance/`。
