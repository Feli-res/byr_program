# 4.11 实施计划：全站交叉检查、AI 效果对比与负载测试

日期：2026 年 11 月 2 日。依据：[计划书 4.11](../../邮智汇_程设项目计划书.md)、[T01 第六节与 AC01—AC20](../../demand/T01_首版需求基线与验收清单.md)、[4.8 使用与验收](../ai48/README.md)、[4.9 使用与验收](../reminders/README.md)、[4.10 使用与验收](../admin/README.md)。

本文只排任务、数据口径、判定和顺序，不写人员分工。4.11 不是再写一遍功能说明，而是拿出可复跑的数字和证据。

## 一、什么算完成

4.11 完成必须同时满足下面五条：

1. **功能与故障**：AC01—AC20 每项都有“操作、预期、实际、是否通过、证据”记录；影响使用的 P0/P1 问题已修复并重跑原失败项，没有用“页面能打开”代替通过。
2. **AI 对比**：500 件商品、40 条需求在比较前冻结；关键词、语义、AI 确认条件三组都在同一数据上跑完；P@5、R@5、NDCG@10、字段准确率、硬约束违规数都有原始结果；40 条全部报告，不只挑表现好的题。
3. **提醒**：至少 20 次应提醒、20 次不应提醒场景全部执行；精确率和召回率如实报告，重复通知数为 0，至少有一次有效提醒。
4. **负载**：固定数据量下，20 个普通请求、10 条聊天连接和后台提醒同时运行至少 5 分钟；每类请求的 P95、达标比例、错误率、索引同步和提醒延迟都有记录。
5. **可交付**：原始 JSON、日志、截图、冻结哈希和复跑命令齐全；未达标项写明原因和后续处理，不能把目标值写成已达成。

4.11 的验收证据统一来自服务器 `youzhihui-411` 隔离栈；本机只用于改代码、写脚本和跑单测，不作为验收环境。试用站生产入口留给 4.12 复验。

以下情况不能算 4.11 完成：只跑关键词搜索就宣称 AI 搜索通过；只跑正常流程不注入故障；只跑浏览器成功路径；只跑 debug 构建就下性能结论；只写“目标 90%”没有实测值；把 411 隔离栈结果冒充试用站生产结果；为了拿数字直接压试用站。

## 三、测量前必须先修的几件事

这些不修，测出来的数字不能代表真实功能。

### 3.1 让 AI 故障可测

- 在 `ai_service.rs` 增加测试专用地址覆盖：只有 `DEV_TOOLS_ENABLED=true` 时才读取 `AI_CHAT_URL`，生产默认仍是 `https://api.deepseek.com/chat/completions`。
- 新增 localhost mock（如 `scripts/ai_mock_411.py`），支持四种响应：正常 JSON、延迟 20 秒、乱格式 JSON、HTTP 500。
- 断言：延迟场景在 15 秒内返回 503 且错误码为 `AI_TIMEOUT`/`AI_UNAVAILABLE`；乱格式和 500 返回 503；页面显示失败并允许手动填写，不显示成功。
- mock 使用假密钥，不读取真实 `DEEPSEEK_API_KEY`。

### 3.2 让类别和品牌真正落到筛选条件

- 文本模型 system prompt 把 `category` 限定为 `数码设备 / 图书资料 / 生活用品 / 其他` 之一；不要再让模型自由输出“平板电脑”。
- 后端增加别名表：`平板/平板电脑/iPad → 数码设备`，`教材/课本/书 → 图书资料`，`日用品/宿舍用品 → 生活用品`；映射后仍由用户在页面上确认或修改。
- 品牌增加规范化：`苹果 → Apple`、`华为 → HUAWEI`、`联想 → Lenovo`、`小米 → Xiaomi`、`索尼 → Sony`、`戴尔 → Dell`、`惠普 → HP`；不确定时保持 `null`，不得猜。
- 这两项只改“解析结果如何落到现有筛选”，不改搜索排序算法。

### 3.3 固定语义阈值口径

当前 4.8 文档写 0.35，代码没有截断。评测前二选一，并写进报告：

- **推荐**：以当前代码“只排序、不截断”为准，删掉文档里的 0.35 表述；no-result 查询单列，观察是否误返回。
- 若课程要求必须有阈值：在 `semantic.rs` 加 0.35 过滤，同步文档，然后重跑全部 40 条，不能只重跑失败题。

### 3.4 固定构建与数据隔离

- 4.11 的功能、浏览器、AI 和负载验收全部在服务器上的 `youzhihui-411` 隔离栈执行；本机只改代码、写脚本和做单测，不把本机结果当验收结果。
- 411 栈用 `cargo build --release` 的 API 镜像和生产前端构建；记录镜像 tag 和 digest，不能用 debug 构建下性能结论。
- 411 栈使用独立的 Compose 项目名、`youzhihui_411` 数据库、独立 Redis、独立 embedding、独立 API/web 容器和独立上传卷；不写 `youzhihui_trial`，不复用试用站的数据卷。
- 开始和结束比较本机 `youzhihui_dev` 三个开发账号的完整用户行，结果必须一致；同时记录试用站容器和数据卷没有变化。

### 3.5 固定模型与版本

- 记录待测 commit、411 镜像 tag/digest、试用站版本（当前 `trial-20261102-01`）、向量模型 `BAAI/bge-small-zh-v1.5`、prompt 的 SHA-256。
- 4.11 的条件理解调用 411 栈的真实模型接口；检索排序、提醒和负载也用 411 栈。4.11 不调用试用站 AI，不占试用站的 AI 预算。
- 如果评测中修改了 prompt 或类别映射，重建/重启 411 栈后重跑 40 条，并记录新镜像；试用站的同步更新留到 4.12。

### 3.7 只在服务器测试的做法

可以只把服务器作为验收环境，但不能直接在试用站上做全部测试。做法是同一台服务器上另起一套 411 隔离栈：

- Compose 项目名固定 `youzhihui-411`，容器名、网络、数据卷都带 `411` 前缀；API 直连端口 `127.0.0.1:18092`，网页入口 `127.0.0.1:18093`，都不开放公网。
- 411 栈有自己的 MySQL、Redis、embedding、API、web、edge（Nginx）和上传卷；`AI_ENABLED=true`，密钥只从服务器私有环境读取，不写进仓库或日志。
- edge 把 `/api/` 和 WebSocket 转给 API，其余转给 web；这样浏览器和试用站一样走同源 `/api/v1`，聊天 WSS/WS 也能测。API 直连端口只给负载脚本用。
- 浏览器验收：在本机用 SSH 隧道把服务器 `18093` 映射到本机 `18093`，打开 `http://localhost:18093`。页面、数据、API、WebSocket 都在服务器，浏览器只是客户端；如果要求完全不在本机运行浏览器，可在服务器安装 Playwright/Chromium，或跑一个浏览器容器。
- 负载验收：负载脚本上传到服务器，在服务器上通过 loopback 压 411 栈；不要从家里网络压公网，否则测到的是宽带和 Nginx，不是服务器处理能力。
- 功能/故障验收：停 411 栈自己的 MySQL/Redis，或只重启 411 的 API；绝不动试用站容器和数据卷。
- 411 栈的 edge 是本机 HTTP Nginx，不是生产 HTTPS 证书链路，所以它验证的是“服务器上的网页、API 和本机 WebSocket”，不是生产入口。生产 Nginx、HTTPS、WSS 和公网链路在 4.7 已验过，4.12 还要在试用站生产栈做一次复验；4.11 报告里要写清这个边界。

资源上给 411 栈设上限，避免挤占试用站：例如 MySQL 512 MB、Redis 128 MB、embedding 1 GB/1 CPU、API 512 MB、web 256 MB；在低峰期跑，先看 `docker stats` 和服务器负载，发现试用站明显变慢就暂停测试。

## 四、工作包与顺序

### W1 基线与环境（约 1 天）

- 冻结待测 commit；记录服务器操作系统、CPU、内存、磁盘、Docker、MySQL、Redis、Rust、Node 版本。
- 在服务器创建 `youzhihui-411` 隔离栈：独立 MySQL/Redis/embedding/API/web/edge(Nginx)/上传卷，独立 `youzhihui_411` 库；API 直连 `18092`，网页入口 `18093`。

### W3 500 件商品与 40 条需求（约 1.5 天）

**商品数据**：500 件，全部为本平台真实可读的商品行，不是只存在 JSON 里。

- 类别覆盖 4 类：数码设备、图书资料、生活用品、其他；至少 2 个校区；价格覆盖免费、低价、中价、超预算边界；成色覆盖 new/like_new/good/fair；品牌覆盖 Apple、HUAWEI、Lenovo、Xiaomi、Sony、Dell、HP 及无品牌；部分商品带 `stylus_support`、`storage_gb`。
- 10 个卖家，每人 50 件；每件 1 张唯一小图，走 411 栈真实上传和发布接口；记录商品 ID、图片 ID、版本、索引状态。

### W4 AI 效果对比与提醒（约 1 天）

**4.11.2 条件理解**

- 在服务器 411 栈的 `youzhihui_411_ai` 库中建 4 个专用测试账号，调用 411 栈 `POST /api/v1/ai/goods-intent`，每账号每分钟最多 5 次，40 条约 2～3 分钟；除限流/预算计数外，不写入帖子、商品、任务等业务数据。
- 保存 `intent-raw.json`：query_id、HTTP 状态、原始 JSON、耗时、时间、411 镜像 tag；不保存 cookie、密码、密钥。
- 字段准确率按 6 个字段逐条比较：category、brand、max_price_cents、campus_code、stylus_support、min_condition；未明确必须为 `null`，多填、错填、漏填都算错。
- 准确率同时报“字段微平均”和“逐字段”，目标都不低于 90%。

**4.11.2 检索对比**

在同一份 500 件商品、同一批 40 条需求上分别跑：

| 组 | 请求 | 说明 |
| --- | --- | --- |
| K 关键词基线 | `/api/v1/search?q=原句&mode=keyword&kind=goods&page_size=10` | 不加载 AI 条件 |
| S 语义 | `/api/v1/search?q=原句&mode=semantic&kind=goods&page_size=10` | 只按意思排序，不加载硬条件 |
| A AI 确认条件 | 先用解析结果构造 `category_id/brand/max_price_cents/campus_code/stylus_support/min_condition`，再请求 `mode=semantic&kind=goods` | 模拟用户确认后的真实 AI 搜索 |

- 记录每组 top-10 的 ID、分数、耗时、`mode_used`、`degraded`；保存 `search-raw.json`。
- 指标：P@5、R@5、NDCG@10，按全部 36 条（排除 4 条无已知结果）做宏平均；另报同义表达 20 条子集。
- 硬约束违规只对 A 组统计：top-10 中任一商品违反用户明确条件（预算、校区、类别、品牌、手写笔、成色、在售状态）即记 1 条；目标为 0。
- 通过条件：字段准确率 ≥90%；硬约束违规数 = 0；A 组和 S 组的 NDCG@10 都不低于 K 组；同义子集 S 组 R@5 > K 组。
- 若 A/S 低于 K：先查是条件提取错、类别映射错还是排序差；只改对应环节，重跑全部 40 条，最多两轮。排序若仍不达标，再考虑关键词+语义 RRF 融合，不在评测前先改算法。
- 两轮后仍不达标，记录为“未通过”并转 4.12 修复；不能改金标、删题或只报部分题目。
- 如果修改 prompt 或类别映射，只重建/重启 411 栈并重跑 40 条；试用站的同步更新留到 4.12，不能把“411 栈结果”写成“试用站已通过”。
- 无已知结果的 4 条不进入 P/R/NDCG 分母，单独报告“返回了几条、top-1 是否相关”。

**4.11.2 提醒对比**

- 20 个应提醒场景：4 个买家，每人 5 个任务；每个任务先完成首轮全量，再发布 1 件符合条件的新商品；预期恰好 1 条 `goods_match` 通知。
- 20 个不应提醒场景：覆盖超预算、错校区、错品牌/类别、缺手写笔、成色不足、已预留、已售、已下架、暂停任务、删除任务、封禁账号、重复执行；预期 0 条新通知。
- 每 5 分钟检查一次；为缩短等待，可在 411 库用 SQL 把 `next_due_at` 置为当前时间模拟到期，但必须记录“这是到期模拟”，不能把 5 分钟周期说成已经自然等待。
- 指标：精确率 = 正确提醒 / 全部提醒；召回率 = 有提醒的正例 / 20；重复通知数 = 同一任务同一商品的第 2 条及以后；延迟 = 商品发布到通知持久化的时间，按正例统计 P95。
- 通过条件：精确率 ≥90%、召回率 ≥90%、重复通知数 = 0、至少 1 条有效提醒、延迟 P95 ≤ 检查周期 + 120 秒。
- 提醒条件用 AI 解析后用户确认的结果，不手工改成“正确答案”；AI 解析错导致漏报/误报，算该项失败并修复后重跑。

产出：`docs/acceptance/ai-eval-411.json`、`docs/acceptance/4.11_AI评测.md`、原始 intent/search 结果、提醒场景结果。

## 五、指标口径

### 5.1 检索指标

- `P@5 = |top5 ∩ 相关集| / 5`；返回不足 5 条时缺位按 0 计。
- `R@5 = |top5 ∩ 相关集| / |相关集|`，只对相关集非空的题计算；无已知结果的题单列，不进入分母。
- `NDCG@10 = DCG@10 / IDCG@10`，相关性用 0/1；IDCG 按相关集前 10 个理想位置计算。
- 汇总用宏平均：先算每题，再对题取平均；同时报全部 36 题和同义 20 题两个子集。
- 字段准确率：每个字段 40 次判断，`正确数 / 40`；再算 6 个字段的微平均。`null` 与具体值同等对待，多填、漏填、错填都算错。
- 硬约束违规：A 组 top-10 中违反任一明确硬条件的商品数；同时报“有违规的题数”。

### 5.2 提醒指标

- 精确率 = 正确提醒数 /（正确提醒数 + 误报数）；误报包括反例通知和重复通知。
- 召回率 = 有有效提醒的正例数 / 20。
- 重复通知数 = 同一任务、同一商品的第 2 条及以后通知总数，目标 0。
- 延迟 = 商品保存成功到 `goods_match` 通知持久化的秒数；正例 P95 与达标比例都要报。

### 5.3 负载指标

- P95 用排序后最近秩或线性插值，报告里写明方法；同一份原始延迟数组同时算 P50/P95/P99。
- 达标比例 = 延迟 ≤ 阈值的请求数 / 该类有效请求数；与 P95 一起报，不能只报平均。
- 错误率 = 非预期失败请求 / 总请求；5xx、超时、连接失败、消息未送达分别计数。
- 索引延迟 = `indexed_at - 源 updated_at`（单条测试）或轮询发现时间；批量预热单独记录。
- 提醒延迟 = 通知 `created_at` - 商品 `created_at`；定时任务排队时间单独记录。

## 七、风险与取舍

1. **模型输出不稳定**：同一句可能返回不同字段。条件理解请求加 `temperature: 0` 并记录；若仍抖动，同一批只跑一次并保存原始结果，不用多次挑最好的一次。
2. **411 栈不是生产入口**：它和试用站同机同镜像，有本机 HTTP edge，但没有生产 HTTPS 证书链路，也不是真实用户数据；4.12 必须在 trial 生产栈复验生产入口，4.11 不把 411 结果写成“试用站已通过”。
3. **索引积压**：500 商品 + 1,000 帖子预热可能超过 10 分钟；必须等 `search_documents` 追平再测，不能把预热中的延迟算成搜索慢。若负载中新增内容导致索引超过 60 秒，记录为问题，修批量/优先级后重跑。
4. **语义阈值**：加 0.35 截断可能提高精度但降低召回；这是产品取舍，必须评测前定，不能看完结果再挑有利口径。
5. **AI 条件理解走 411 栈**：只写 411 的限流/预算和临时业务数据；如果修改 prompt，只重建 411 栈并重跑，试用站更新留到 4.12。
6. **相似帖子提示**：未实现，4.11 不测试、不写成通过；在报告中注明“选做未实现”。
7. **服务器资源争用**：411 栈和试用站、其他人的服务共用 4 核 16 GB；完整 411 栈按上限约 2.4 GB，启动前 `MemAvailable` 必须至少 2.5 GB。当前可用内存不足时，先协调释放内存或改用“只起 API/web/edge、复用现有 MySQL/Redis/embedding”的轻量方案，但后者会与试用站共享资源，不能做停库类故障注入。必须设容器内存/CPU 上限、在低峰期跑、看 `docker stats` 和 `uptime`；试用站明显变慢就暂停测试。
8. **清理误伤**：411 栈必须用固定项目名 `youzhihui-411`，删除时只执行 `docker compose -p youzhihui-411 down -v`；禁止对 `youzhihui-trial` 执行 `down -v`、`docker volume prune` 或批量删卷。
9. **时间不足**：优先保 4.11.1 的 P0/P1 和 4.11.2 的硬指标；不要因为赶时间直接压试用站，宁可把负载/复验留给 4.12。
