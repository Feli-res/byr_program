# 4.11.3 负载测试结果

日期：2026-11-03。环境：服务器 `youzhihui-411` 隔离栈，4 vCPU / 16 GiB 宿主机；411 slice 上限 1.5 CPU，API 1 CPU / 512 MiB，MySQL 512 MiB / 1 CPU，embedding 1024 MiB / 1 CPU。**结果是在 1.5 CPU 隔离配额下测得，不能等同于整机 4 核性能。**

**2026-11-03 16:10 更新：首测发现的索引、WebSocket 1013 和语义降级已修复并复测，修复后结果见 [修复后负载测试](4.11_负载测试_修复后.md)。** 本文保留首测的失败证据，便于对比，不再代表当前状态。

原始结果：[首轮 5 分钟](load-411.json)、[诊断轮 3 分钟](load-411-diagnostic.json)。数据准备和启动记录见 [压测准备](4.11_压测准备.md)、[隔离栈](4.11_服务器隔离栈.md)。

## 一、结论

**4.11.3 部分通过，不能标记为全部通过。**

- 普通列表、详情、发帖、评论、关键词搜索、语义搜索、聊天延迟、提醒延迟的 P95 都低于目标，且成功样本的达标比例均不低于 95%。
- 但 **语义索引同步未达标**：新增商品在 120 秒内不可见；压测后仍有 775 个索引任务 pending，最大索引滞后 1901 秒，新商品 501—506 未进入索引。
- **WebSocket 连接稳定性未达标**：首轮 10 条连接中有 5 次 `1013 (try again later)` 关闭；诊断轮仍有 1 次。成功送达的消息 P95 合格，但“连接经受 5 分钟混合负载”不能算通过。
- **语义搜索降级比例偏高**：诊断轮 914 次语义调用（含预热）中 247 次（27.0%）回退为关键词搜索（`degraded=true`）；测量窗口内共 800 条语义请求，模式计数包含 30 秒预热，不能把 247/800 当作精确比例。组合响应时间合格，但约四分之一以上请求不是按意思搜索。

## 三、方法与样本

- 20 个并发 HTTP 工作线程，循环混合：列表 25%、详情 20%、发帖 10%、评论 10%、关键词搜索 15%、语义搜索 10%、商品/帖子详情 10%；单线程间隔 200～450 ms。
- 10 条 WebSocket（5 对用户）同时在线，每对每 8～13 秒互发一条消息，测量发送到对方收到 `message.created` 的时间。
- 100 个提醒任务后台运行；5 个受控正例任务在测量开始前由脚本发布匹配商品，测量商品保存到 `goods_match` 通知持久化的时间。
- 首轮：预热 60 秒，连续采样 300 秒（5 分钟）；诊断轮：预热 30 秒，采样 180 秒，专门记录语义搜索的 `mode_used/degraded`，不重复造提醒商品。

## 五、对服务器和试用站的影响

- 411 栈始终在独立 slice 内运行；宿主可用内存从约 13.4 GB 降至最低约 13.3 GB，未触发 OOM。
- 压测期间宿主机 load average 最高约 4.93（4 核），411 的 API/MySQL/embedding 分别约 13%/45%/81% 容器 CPU；试用站 API 仍只有约 0.2% CPU。
- 保护监控每 5 秒采样：试用站 readiness 全程成功，耗时约 2～10 ms；`low_memory`、`swap_growth`、`cpu_saturated`、`trial_degraded`、`disk_low` 均未触发；无 411 OOM。
- 试用站 5 个容器 ID 与压测前完全一致，4 个数据卷名称未变化；压测只写 `youzhihui_411` 库和 411 上传卷。
- 结论：本次负载对试用站数据无影响，短时资源竞争存在，但试用站可用性保持正常；这不代表长期高负载下仍无影响。

## 六、未通过项与下一步

1. **索引吞吐不足（P1）**
   - 现象：单条新增商品 120 秒不可见；积压 775 个任务，最大滞后 1,901 秒。
   - 原因方向：索引 worker 每 5 秒最多处理 10 条，写入负载持续产生新帖；embedding 调用在 1 CPU 配额下频繁超时（日志多次 `semantic index update deferred`）。
   - 处理：提高批处理量/并发、优先处理商品与编辑、把 embedding 与 API 的 CPU 配额分开；修复后重跑单条 60 秒检查和 5 分钟负载。不能把本次结果标成索引达标。

2. **WebSocket 1013（P1）**
   - 现象：首轮 5 次、诊断轮 1 次连接关闭；成功消息延迟正常。
   - 原因方向：实时连接每 500 ms 做会话/事件检查，混合负载下会话查询或事件 payload 超时；具体触发点需用 API 日志和更低 HTTP 并发复现。
   - 处理：复现并定位 `valid()`/事件 payload 的超时分支；修复后重跑 10 条连接 5 分钟，记录连接建立数、异常关闭数和消息丢失数。

3. **语义降级约 27%（P1）**
   - 现象：诊断轮 247/914 次调用（含预热）回退关键词；测量窗口内 800 条语义请求，首轮未单独记录 `mode_used`，不能宣称纯语义 P95。
   - 处理：提高 embedding 并发/超时或降低索引与查询争用；重跑时按 `semantic`/`keyword` 分开统计 P95 和降级率，目标是不把关键词结果算成语义结果。

4. **数据口径偏差（P2）**
   - 实际 6 个会话承载 2,000 条消息，不是计划的 25 个会话；不影响消息量、历史和实时链路，但报告必须如实写明。

5. **清理**
   - 本轮结束后已停止 411 的六个容器并保留数据卷供复跑；试用站五个容器 ID 未变化，试用站健康检查正常。当前不删除 411 卷，避免丢失复跑数据；删除前需确认不再需要 4.11 数据。

## 七、判定

- **HTTP 延迟目标：通过**（八类成功样本的 P95 和 ≥95% 达标比例均满足；索引单列失败）。
- **提醒延迟：通过**（5/5，P95 108.8 秒 ≤420 秒；但样本数不足以替代 20+20）。
- **索引同步：未通过**（>120 秒仍不可见，积压 775，最大滞后 1,901 秒）。
- **聊天连接稳定性：未通过**（5 次/1 次 `1013` 异常关闭；成功消息延迟合格）。
- **语义搜索有效性：部分通过**（响应时间合格，约 27% 的语义调用降级为关键词）。

因此 AC19 只能记为“**部分通过**”，待索引、WebSocket 和语义降级修复后重跑；4.12 不能直接引用本次结果宣称负载验收通过。
