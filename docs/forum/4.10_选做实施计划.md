# 4.10 选做实施计划：论坛体验扩展

日期：2026 年 11 月 2 日。依据：[计划书 4.10](../../邮智汇_程设项目计划书.md)、[综合论坛创新方向](../../demand/邮智汇_综合论坛创新方向.md)、[4.10 已完成的必做部分](../admin/README.md)。

本文规划 4.10“论坛体验扩展（选做，待实现）”的取舍和实现顺序。选做不改变 4.11、4.12 的必做范围，也不把规划内容写成已完成。

## 一、计划书里的选做具体是什么

计划书 4.10 末尾列了三项，原意如下：

| 选做项 | 计划书要求 | 当前状态 |
| --- | --- | --- |
| 社区首页 | 展示最新帖子、热门帖子和板块入口；后端只返回公开可见内容；热门优先看近期互动并随时间衰减；检查空列表、分页和隐藏帖不可见 | 部分具备：`/` 现在只有公告条和完整帖子列表，`/posts` 有“最新/点赞与讨论”排序和板块导航；没有独立的最新/热门/板块概览 |
| 校园求助帖 | 区分普通帖和求助帖；显示待解答、已解决和有帮助的回复；后端保存类型和状态；只允许有权用户修改；检查回复归属、筛选和刷新后的状态 | 未实现：`posts` 没有类型/解决状态，评论没有“有帮助”标记 |
| 组队招募、板块管理 | 有余力时增加招募期限与状态，或让管理员新增、调整、停用板块；先确定停用后历史帖子的展示和权限规则 | 板块管理已完成：管理员可新建、改名/说明、启用/停用，停用后不能新发帖、历史帖仍可读；招募未实现；板块显示顺序未做 |

另外两项要分清：

- **论坛侧“相似帖子提示”**属于 4.8 的论坛 AI 选做，不属于 4.10 这三项；它需要语义检索、权限过滤和单独评测，不能和本次选做混在一起做。
- **“我关注的板块”**只是创新方向里的远期想法，计划书 4.10 没有把它列为本次任务，本次不做。

## 二、推荐范围

按“先低风险、先演示价值、后扩展”的顺序：

| 优先级 | 内容 | 建议 | 理由 |
| --- | --- | --- | --- |
| P1 | 社区首页 + 热门排序 | 做 | 不改表也能先上线；首页是答辩第一眼看到的内容 |
| P2 | 校园求助帖 | 做 | 直接体现“综合论坛”的校园实用性，和普通讨论区分明显 |
| P3 | 组队招募 | 有余力再做 | 字段和状态最多，最容易拖慢 4.11/4.12 |
| 不做 | 板块显示顺序/版主自主管理 | 暂不做 | 4.10 必做的板块管理已经完成，顺序和自主管理不是当前重点 |
| 另排期 | 相似帖子提示 | 单独排期 | 属于 4.8 选做，需要语义检索和效果评测 |

**结论：**若时间只够一轮，做“社区首页 + 校园求助”；组队招募放在 4.11 之后、4.12 之前视剩余时间决定。三项都做预计 8～10 人日；只做首页约 2 人日，首页加求助约 5～6 人日。

## 三、数据设计

### 3.1 新增迁移 0008（求助与招募一起）

不改 `0001—0007`。建议用一个 `0008_forum_optional.sql`，避免同一批功能拆成多个版本：

```sql
ALTER TABLE posts
  ADD COLUMN post_type ENUM('discussion','help','recruit')
    NOT NULL DEFAULT 'discussion' AFTER body_markdown,
  ADD KEY ix_post_type_feed(post_type,visibility,deleted_at,pinned,created_at,id);

CREATE TABLE post_help_details (
  post_id BIGINT UNSIGNED PRIMARY KEY,
  status ENUM('open','solved') NOT NULL DEFAULT 'open',
  updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
    ON UPDATE CURRENT_TIMESTAMP(6),
  FOREIGN KEY(post_id) REFERENCES posts(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE post_recruit_details (
  post_id BIGINT UNSIGNED PRIMARY KEY,
  deadline DATETIME(6) NOT NULL,
  capacity SMALLINT UNSIGNED NOT NULL,
  status ENUM('open','closed') NOT NULL DEFAULT 'open',
  location VARCHAR(100) NOT NULL,
  updated_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6)
    ON UPDATE CURRENT_TIMESTAMP(6),
  KEY ix_recruit_open(status,deadline),
  FOREIGN KEY(post_id) REFERENCES posts(id),
  CHECK (capacity BETWEEN 2 AND 100),
  CHECK (CHAR_LENGTH(location) BETWEEN 2 AND 100)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE post_helpful_marks (
  post_id BIGINT UNSIGNED NOT NULL,
  comment_id BIGINT UNSIGNED NOT NULL,
  user_id BIGINT UNSIGNED NOT NULL,
  created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY(post_id,comment_id),
  KEY ix_helpful_user(user_id),
  FOREIGN KEY(post_id) REFERENCES posts(id),
  FOREIGN KEY(comment_id) REFERENCES comments(id),
  FOREIGN KEY(user_id) REFERENCES users(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

另加热门查询用的索引：

```sql
ALTER TABLE post_likes ADD KEY ix_like_recent(created_at,post_id);
ALTER TABLE comments ADD KEY ix_comment_recent(created_at,post_id);
```

选择“扩展表”而不是给 `posts` 加一排空列，是为了让普通帖不携带求助/招募字段，避免用大量 `NULL` 和检查约束表达三种类型。`post_type` 仍放在 `posts`，方便列表筛选和排序。

### 3.2 字段与状态

| 类型 | 存储 | 公开显示 |
| --- | --- | --- |
| 普通讨论 | `post_type='discussion'`，无扩展行 | 普通帖 |
| 校园求助 | `post_type='help'` + `post_help_details.status` | 待解答 / 已解决 |
| 组队招募 | `post_type='recruit'` + `post_recruit_details` | 招募中 / 已结束 / 已截止 |

- 招募状态存 `open/closed`，是否过期由 `deadline` 和当前时间计算，不依赖后台定时任务：
  - `closed`：发布者提前结束；
  - `expired`：`deadline` 已过；
  - `open`：未关闭且未过期。
- 发布后不允许改类型：普通帖、求助帖、招募帖的字段和页面行为不同，允许互转会留下不完整的详情行；如确实需要，先删除再重发。
- 求助帖发布时 `status='open'`；只有提问者可以标记已解决或重新打开。
- 招募人数只作展示，不做在线报名、审核或名额扣减；联系仍通过评论或私信。

## 四、接口设计

### 4.1 发帖和编辑

`POST /api/v1/posts` 增加可选字段：

```json
{
  "board_id": "1",
  "title": "沙河周末哪里可以打印资料",
  "body_markdown": "……",
  "post_type": "help",
  "recruit": null
}
```

- `post_type` 缺省为 `discussion`；`help` 时在同一事务插入 `post_help_details`。
- `recruit` 时必填：

```json
{"post_type":"recruit","recruit":{"deadline":"2026-11-10T12:00:00Z","capacity":4,"location":"沙河校区图书馆"}}
```

- `deadline` 必须晚于当前时间且不超过 60 天；`capacity` 2～100；`location` 2～100 字。
- 普通讨论或求助帖携带 `recruit`、招募帖缺少 `recruit`，都返回字段校验错误，不能静默忽略。
- `PATCH /posts/{post_id}` 不接收 `post_type`；编辑正文/标题/附件沿用现有版本检查。招募信息另走专门接口，避免编辑表单误改状态。

### 4.2 列表与首页

`GET /api/v1/posts` 增加筛选：

| 参数 | 允许值 | 说明 |
| --- | --- | --- |
| `type` | `discussion`、`help`、`recruit` | 不填为全部 |
| `help_status` | `open`、`solved` | 仅 `type=help` |
| `recruit_state` | `open`、`ended` | 仅 `type=recruit`；`ended` 含提前结束和已过期 |
| `sort` | `latest`、`popular`、`hot` | `hot` 为新增 |

`hot` 排序规则（固定、可解释，不做复杂推荐）：

```text
score = (1 + 3×近7天点赞数 + 5×近7天公开评论数)
        × POW(0.5, 帖子年龄小时数 / 168)
```

- 置顶仍优先；同分按创建时间、id 倒序。
- 只统计公开、未删除的帖子和评论；隐藏内容不进入任何首页列表。
- 7 天半衰期意味着旧帖不会因为历史点赞多而长期霸榜；没有互动的新帖也会随时间自然下降。

新增 `GET /api/v1/forum/overview`（公开）：

```json
{
  "latest": [PostSummary, ...5],
  "hot": [PostSummary, ...5],
  "boards": [{"id":"1","name":"学习交流","description":"...","post_count":42,"last_activity_at":"..."}],
  "help_open": [PostSummary, ...5],
  "recruiting": [PostSummary, ...5]
}
```

- 每个列表最多 5 条；没有内容时返回空数组，前端显示空状态。
- `boards` 只含启用板块；`post_count` 只计公开未删除帖子；`last_activity_at` 取该板块最近公开帖时间。
- 概览只是聚合查询，不新增缓存表；数据量到 4.11 的 1,000 帖仍可直接查询，若变慢再加索引或缓存。

### 4.3 求助状态和“有帮助”

`PATCH /api/v1/posts/{post_id}/help`：

```json
{"status":"solved","version":3}
```

- 仅提问者；仅求助帖；`public`、未删除；版本匹配。
- 允许 `solved → open` 重新打开；修改后版本 +1。
- 版主/管理员只能隐藏帖子，不能代替提问者标记解决。

`PUT /api/v1/posts/{post_id}/comments/{comment_id}/helpful`、`DELETE` 同路径：

- 仅提问者；仅求助帖；评论必须属于同一帖子、公开且未删除；不能标记自己的回复。
- 重复 PUT 幂等，返回当前 `count`；DELETE 幂等。
- 返回 `{"helpful":true,"count":2}`。
- 评论 DTO 增加 `helpful_count`；帖子详情对提问者额外返回 `helpful_comment_ids`，前端据此显示“已标记”。
- 评论被隐藏后不再显示标记和计数；恢复后标记仍在，不复制数据。

### 4.4 招募状态

`PATCH /api/v1/posts/{post_id}/recruit`：

```json
{"version":4,"status":"closed"}
```

- 仅发布者；仅招募帖；版本匹配。
- 允许修改 `deadline`、`capacity`、`location`；`status` 只能 `open/closed`。
- 重新开放必须同时满足 `deadline` 仍在未来；已过期需先延长截止时间再开放。
- 截止时间只按 UTC 保存，页面按上海时区显示；不在后台跑定时任务改状态。
- 返回更新后的帖子；`recruit_state` 由后端计算为 `open/closed/expired`。

## 五、前端实现

### 5.1 社区首页

新增 `components/forum/home.js`，`app/page.js` 使用它；保留顶部公告条。

- 板块入口：卡片显示板块名、简介、帖子数；点击进入 `/posts?board_id=...`。
- 最新讨论、近期热门：各 5 条，显示类型标签、标题、板块、作者、时间、点赞/回复数；点击进详情。
- 待解决求助、正在招募：有内容才显示；分别链接到筛选后的列表；招募显示截止时间。
- 底部“查看全部讨论”进入 `/posts`；空数据显示“还没有帖子，发布第一篇”。
- 加载、失败、空列表分开显示；概览失败不影响公告和主导航。
- 窄屏改单列，不横向溢出。

### 5.2 列表和详情

- `/posts` 增加类型标签页：全部、讨论、求助、招募；求助下增加“待解答/已解决”，招募下增加“招募中/已结束”；排序增加“近期热门”。
- 所有筛选写入网址，翻页/返回保留；与现有板块筛选兼容。
- 帖子详情：
  - 类型标签：求助、招募；
  - 求助：状态、提问者“标记已解决/重新打开”、每条回复的“有帮助”按钮与计数；
  - 招募：截止时间、人数、地点、状态，发布者“结束招募/重新开放/修改信息”；
  - 隐藏帖沿用现有规则，不显示这些操作。
- 我的帖子和管理列表显示类型标签；管理操作仍只做置顶/隐藏/恢复，不改变类型和求助/招募状态。

### 5.3 发帖编辑器

- 顶部增加“帖子类型”：普通讨论 / 校园求助 / 组队招募；编辑已有帖子时只读显示类型。
- 选“求助”时提示发布后可在详情标记解决，不增加必填项。
- 选“招募”时展开截止时间（`datetime-local`）、人数、地点，前端先校验，后端再校验。
- 保留现有附件、预览、版本冲突和失败提示；类型切换时清空不适用的字段，避免提交混合数据。

## 七、验收清单

### 7.1 首页和热门

- 首页显示板块入口、最新 5 条、热门 5 条；没有内容时显示空状态。
- 隐藏、删除、停用板块的帖子不出现在任何首页列表；分页链接可用。
- 同样互动量下，新帖排在旧帖前；旧帖高历史点赞不能长期压过近期互动。
- 首页在 390px 宽度下无横向溢出；概览接口失败时页面仍有明确重试/占位。

### 7.2 求助帖

- 可发布求助帖；普通帖/求助帖在列表和详情有明确区分。
- 只有提问者能标记已解决/重新打开；他人、版主、管理员调用被拒绝；版本冲突返回 409。
- 只有提问者能标记有帮助；不能标记自己的回复；重复标记不重复计数；隐藏评论不显示标记。
- 刷新、重启后状态和标记仍在；`help_status=open` 筛选只返回待解决。
- 隐藏/删除的求助帖不出现在列表和首页，也不能继续改状态。

### 7.3 招募帖

- 发布时截止时间、人数、地点校验正确；过去时间、缺字段、超范围被拒绝。
- 列表“招募中”不返回已结束/已过期；“已结束”同时包含提前结束和过期。
- 发布者可提前结束；截止前可延长并重新开放；过期后不延长不能开放。
- 非发布者不能改；隐藏/删除帖不能改；刷新和重启后状态正确。

### 7.4 迁移和回归

- 从 0007 升级到 0008 后，旧帖子默认 `discussion`，旧数据、附件、评论、搜索均正常。
- 更新所有断言迁移数为 7 的脚本和文档，避免升级后误报。
- 论坛、商品、聊天、账户、4.10 管理和 4.6 整体验收全部重跑。
- OpenAPI/HTTP 目录/页面映射重新生成；旧客户端不传新字段仍可用。

## 八、风险和边界

1. **迁移数量连锁改动**：`verify_acceptance.py`、`verify_ai48.py`、`verify_chat.py` 和若干文档写死了 7 个迁移；实施 0008 时必须同步改为 8，并重跑升级检查。
2. **契约严格**：现有响应校验使用 `additionalProperties:false`，新增字段必须同时改 `Post`、`PostSummary`、`Comment` 和请求体，否则论坛/验收测试会失败。
3. **首页改动影响现有入口**：`/` 从帖子列表改为概览后，`/posts` 仍是完整列表；公告条和 4.10 浏览器检查要保留。
4. **热门公式不要写成“算法推荐”**：它只是近期互动加时间衰减的排序，答辩时不要声称个性化推荐。
5. **不做在线报名**：招募人数只是展示，不校验报名者、不扣名额、不做审核；联系仍用评论/私信。
6. **不改变管理边界**：版主/管理员不能替提问者标记解决、不能替发布者结束招募；他们仍只能按现有治理规则隐藏/恢复帖子。
7. **优先保证 4.11/4.12**：选做不应挤占 20 项验收、AI 对比、负载和独立备份恢复；如果时间冲突，先完成必做，再回到本计划。

## 九、建议的最终取舍

- **推荐先做**：社区首页 + 近期热门（P1）。它不改必做流程，能直接改善答辩第一屏，失败也可退回原列表。
- **推荐第二批**：校园求助帖（P2）。它最能体现“综合论坛”与普通论坛的差异，且不依赖 AI。
- **视时间决定**：组队招募（P3）。字段多、状态多，建议在 4.11 结果出来后再决定是否投入。
- **暂不做**：板块显示顺序、版主自主管理、相似帖子提示；前两项不是 4.10 必做，最后一项属于 4.8 选做，另行规划。
