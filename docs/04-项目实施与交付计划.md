# AI 校园二手交易社区项目实施与交付计划

## 1 文档说明

本文档维护团队分工、开发阶段、早鸟策略、测试安排、书面报告、现场汇报、风险和最终交付物。
产品范围参见 [产品需求分析](01-产品需求分析.md)
AI 任务参见 [AI 创新与评价方案](02-AI创新与评价方案.md)
系统模块参见 [系统概要设计](03-系统概要设计.md)

## 2 项目范围基线

首个可提交版本必须完成：

1. 用户注册、登录和模拟校园身份。
2. 商品发布、浏览、筛选、上下架和状态管理。
3. 求购需求及 AI 求购实时观测。
4. 买卖双方私信空间和全局消息中心。
5. 报价、交易确认、完成和评价。
6. AI 商品发布助手。
7. 商品触发匹配、去重通知和匹配解释的基础版本。
8. AI 交易确认卡。
9. 管理员举报和下架。
10. 固定测试集、测试结果、部署说明和演示脚本。

P1 和 P2 功能只有在上述闭环稳定后才能进入开发，不能为了增加功能数量影响可提交版本。

## 3 团队分工

### 3.1 四人组建议

| 角色 | 主要职责 | 主要交付物 |
| --- | --- | --- |
| 项目与基础后端负责人 | 需求管理、用户、商品、权限和数据库 | 需求文档、数据库设计、用户商品接口 |
| 交易与消息负责人 | 求购任务、通知、私信、报价、交易状态和评价 | 私信与交易接口、状态机、接口测试 |
| AI 负责人 | 图片分析、需求解析、语义匹配、确认卡和评价 | AI 服务、提示词、测试集、评价结果 |
| 前端与测试部署负责人 | 页面、联调、自动化测试、部署和演示环境 | 前端页面、测试报告、部署脚本 |

分工可按成员能力调整，但每个核心功能必须有负责人和复核人。不能由一名成员独自承担全部 AI、后端和文档工作。

### 3.2 公共任务

- 全员参与需求评审和核心方案选择。
- 接口变更先更新说明，再进行联调。
- 每周进行进度同步和风险检查。
- 每位成员保存提交、Pull Request、测试和负责模块记录。
- 负责功能的成员同步提供报告材料，避免结项时集中补写。

## 4 Git 协作规范

- `main` 分支保持可运行或可演示。
- 功能分支使用 `feat/功能名称`。
- 缺陷分支使用 `fix/问题名称`。
- 文档分支使用 `docs/文档名称`。
- 提交信息说明实际修改，避免“更新一下”等模糊描述。
- 合并前至少完成一次代码检查和基本测试。
- 禁止提交密钥、密码、真实个人数据和大型临时文件。
- 需求编号、模块名称和状态名称在代码与文档中保持一致。

## 5 开发阶段与里程碑

| 阶段 | 目标 | 主要产出 |
| --- | --- | --- |
| 第一阶段 需求冻结 | 确定 P0、用户流程和三项 AI 功能 | 需求分析、用例、分工 |
| 第二阶段 基础交易闭环 | 完成用户、商品、私信、报价和交易状态 | 可运行的非 AI 版本 |
| 第三阶段 AI 发布助手 | 跑通图片输入、结构化输出和用户确认 | 发布助手 MVP、字段测试集 |
| 第四阶段 求购守望 | 完成需求解析、触发匹配、通知和去重 | 匹配 MVP、检索测试结果 |
| 第五阶段 交易确认 | 完成确认卡和双方确认 | 确认卡 MVP、对话测试集 |
| 第六阶段 测试优化 | 修复问题并形成量化评价 | 功能与 AI 质量报告 |
| 第七阶段 交付答辩 | 固化环境、文档和演示 | 四类报告、PPT、视频或现场环境 |

每个阶段结束时应满足“代码可运行、文档已更新、关键测试已执行”三个条件。

## 6 早鸟提交策略

先完成一条纵向链路，而不是同时开发大量孤立页面：

```text
测试账号登录
→ 卖家发布商品
→ 买家保存求购需求
→ 新商品触发匹配通知
→ 买家进入商品私信
→ 双方协商并确认交易
→ 商品进入已预订和已完成状态
```

纵向链路可运行后，再补充管理后台、页面美化、风险检查和统计面板。早鸟版本可以使用简单轮询和数据库调度器，不应等待 WebSocket、消息队列或复杂推荐模型完成。

## 7 测试与验收安排

### 7.1 功能测试

- 用户权限和越权访问。
- 商品 CRUD、图片和状态转换。
- 求购任务状态和有效期。
- 私信入口、会话复用、历史消息和未读状态。
- 报价、双方确认、并发预订和取消。
- 举报、审核和管理员操作记录。

### 7.2 AI 测试

- 商品字段和缺失信息准确率。
- 需求条件提取准确率。
- 匹配 Recall@5、通知准确率和重复通知率。
- 交易确认卡字段准确率。
- 风险提示准确率和误报率。
- 模型超时、失败和降级测试。

### 7.3 演示前检查

- 固定测试账号可以正常登录。
- 演示图片和商品数据已准备。
- 求购任务和匹配触发可以重复演示。
- 模型额度和网络可用。
- 备用录屏与缓存结果可用。
- 数据库可恢复到演示初始状态。

## 8 书面报告规划

### 8.1 需求分析

- 项目背景、目标用户和校园场景。
- 卖家、买家和管理员痛点。
- 用户角色、用例、P0/P1/P2 范围。
- 功能与非功能需求。
- AI 创新点及验收指标。

主要来源为 [产品需求分析](01-产品需求分析.md) 和 [AI 创新与评价方案](02-AI创新与评价方案.md)。

### 8.2 概要设计

- 总体架构和模块边界。
- 前端、后端、AI 服务和数据库关系。
- 商品发布、求购匹配、私信和交易流程。
- 数据实体、权限、安全和异常处理。

主要来源为 [系统概要设计](03-系统概要设计.md)。

### 8.3 详细设计

- 数据表、字段、索引和约束。
- API 请求、响应和错误码。
- 商品、求购、会话和交易状态机。
- 类图、时序图和核心模块说明。
- AI JSON Schema、提示词、排序规则和异常处理。

详细设计需要在技术栈和接口确定后单独编写，不应在当前阶段虚构实现细节。

### 8.4 结项报告

- 完成情况、功能截图和部署方式。
- 小组任务和个人贡献。
- 测试集、评价指标和实际结果。
- AI 功能对照实验。
- 问题、解决方案和迭代记录。
- 未完成需求、项目局限和后续改进。

## 9 现场汇报方案

使用两个普通账号和一个管理员账号，按照同一故事演示：

1. 卖家上传显示器图片。
2. AI 生成商品草稿并提示缺少型号和点亮照片。
3. 买家保存当前无法匹配的长期购买需求。
4. 卖家发布符合条件的新商品。
5. 系统触发匹配，买家收到站内通知和匹配解释。
6. 买家从通知进入商品详情，再进入私信并提交报价。
7. 卖家从消息中心回复。
8. AI 生成交易确认卡并指出未确认事项。
9. 双方确认，商品进入已预订状态。
10. 完成交易和评价。
11. 管理员查看一条举报或风险记录。
12. 展示固定测试集上的评价结果和失败案例。

该故事同时展示完成度、校园适用性、AI 创新、系统难度和模块协作。

## 10 评分项对应策略

| 评分项 | 项目策略 |
| --- | --- |
| 完成度 10 | 跑通发布、守望匹配、私信、确认、完成和评价闭环 |
| 适用性 10 | 使用校区、自提、毕业季、教材和宿舍用品等校园特征 |
| 创新性 10 | AI 参与内容结构化、持续供需匹配和交易确认 |
| 现场汇报 10 | 使用连贯故事演示正常流程、异常和降级 |
| 小组分工 5 | 模块负责人明确，提交、PR、测试和文档记录可查 |
| 难度 5 | 包含图片理解、语义检索、调度通知、私信和状态联动 |
| 书面报告 | 按需求、概要、详细、结项持续积累材料 |
| 早鸟分 | 先提交可运行的 P0 纵向链路，再迭代 P1 |

## 11 主要风险

| 风险 | 影响 | 应对方案 |
| --- | --- | --- |
| 现有后端只有架构 | 用户、商品和交易仍需开发 | 使用最小数据模型，不照搬大型电商系统 |
| 模型接口不稳定 | 开发和演示受阻 | 超时、缓存、备用适配器和录屏 |
| 图片识别幻觉 | 商品描述失真 | 标记不确定字段，卖家确认后发布 |
| 需求解析错误 | 匹配结果不符合要求 | 展示结构化条件并允许修改 |
| 通知过多 | 用户受到打扰 | 阈值、去重、冷却时间和每日上限 |
| 缺少真实数据 | 推荐和估价无法验证 | 使用低数据依赖方案和人工标注测试集 |
| 功能范围过大 | 无法按时完成 | 冻结 P0，P1 和 P2 延后 |
| 分工不清 | 重复开发或任务遗漏 | 设置负责人、复核人和验收条件 |
| 报告集中补写 | 设计与实现不一致 | 每个里程碑同步更新报告材料 |
